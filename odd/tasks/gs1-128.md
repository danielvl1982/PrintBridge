# GS1-128 (the GS1 standard identifier for logistic units)

Status: DONE and confirmed working by the user on 2026-10-13 (browser, real printing and scanning; see "Browser and printer checks"; S1-S5 implemented 2026-10-13, see Commits and "Browser and printer checks pending"; started on `feat/gs1-128`; added 2026-10-09 at the user's request). Reference named by the user: "GS1-128, GS1 Spain: the standard
identifier for logistic units". Branch when started: `feat/gs1-128`. Create the Engram mirror `odd/gs1-128/tasks` before the first write.

## Objective
Support GS1-128 labels in the three languages: a Code 128 symbol that starts with FNC1 and carries GS1 Application Identifiers (AI),
e.g. `(00)` SSCC, `(01)` GTIN, `(10)` lot, `(17)` expiry, `(21)` serial, `(37)` count, `(400)` order number; read, drawn, edited, written
and converted between TPCL, TSPL and ZPL.

## What GS1-128 needs (to verify against the GS1 General Specifications and the printer manuals before designing)
- Data entered as AI element strings with parentheses `(01)09501101530003(17)250101(10)ABC123`; the symbol encodes the AIs without the
  parentheses; the human readable line keeps them.
- FNC1 as the first symbol character after the start character (what makes it GS1-128 instead of plain Code 128), and FNC1 as the separator
  after a variable-length AI (the last element does not need one). The model already has an FNC1 character (`PB.barcodeData.FNC1` in
  js/core/model.js; TPCL writes it as `>8`).
- Fixed-length AIs table (so the separator is only written after variable-length AIs) and the check digit rules (GTIN-8/12/13/14 and SSCC
  mod 10, the check digit being part of the data you type: the app validates it and shows the expected digit, it never adds it).
- Code 128 subset switching to numeric pairs (code set C) is what the existing Code 128 encoder already does; confirm it handles FNC1 in
  set C and the mid-symbol FNC1.

## What the manuals say the printers support (found by a keyword search, to be read in detail)
- TPCL: `XB` type `N` is listed as `UCC/EAN128` in B-SV4 (2004) and B-452-R (2012), with its check options ("UCC/EAN128 Modulus 10 +
  Modulus 103"). The app does not draw it today.
- TSPL: `BARCODE ... "EAN128"` (already read as Code 128 per the README, with the content kept).
- ZPL: `^BC` with mode `U` (UCC case mode) / `D` (UCC/EAN mode, later guides) and the `>8` FNC1 start code; the README says `e` (UCC check digit) and
  `m` are read, kept and not applied.

## Decisions
- 2026-10-13 (user): AI scope = the **logistic subset** only: 00, 01, 02, 10, 11, 13, 15, 17, 20, 21, 30, 37, 240, 241, 400, 410-415.
  The rest of the GS1 General Specifications AI table is **out of scope**: it is not modelled, validated or converted, and the docs
  (README, Limitations) must say so. An AI outside the subset gets a diagnostic, never silent acceptance.

- 2026-10-13 (user): input notation = the **standard GS1 notation with parentheses** only, e.g. `(01)09501101530003(17)250101(10)ABC123`.
  Raw FNC1-separated data is not accepted as GS1-128 input (it stays a plain Code 128). The app derives the FNC1 separators from the
  fixed / variable length of each AI.
- 2026-10-13 (user): add a GS1-128 sample template (an SSCC pallet label) to the Ejemplo combo, in the three languages.

## S1 findings (2026-10-13, read-only exploration; page numbers are the manuals' own)
- TPCL `XB` type `N` (B-SV4 6.3.9 pp. 63-64, p. 239): exactly 19 digits; the printer adds FNC1, mod 10 and mod 103. Any other length is not drawn.
  So it only fits an SSCC-like symbol. A general element string goes through TPCL Code 128 (type `9`) with `>8` written by the app. Parentheses
  are never accepted by the printer.
- TSPL `EAN128` (B-442/443 pp. 24-27): the local manual only says "Code 128, automatic subset switching". The "EAN128 prepends FNC1" claim comes from
  the TSC TSPL v3.0 manual, which is not in `docs/` (unverified). Reliable FNC1: `128M` with `!102` (the writer already does it, tspl.js:138-146).
- ZPL `^BC` (Vol. 1 pp. 57-62): mode `U` = 19 digits (more is dropped, less is padded with zeros); mode `D` is not in Vol. 1 / 2 (unverified);
  FNC1 is `>8`; the printer adds FNC1 on its own only in mode U; what `e=Y` does is not explained.
- Consequence (corrected in S5): the app writes the FNC1s itself and emits plain Code 128 data in all three languages; the mod-10 digit is VALIDATED (the expected digit is shown in the error), never added (js/components/barcode/gs1.js `checkElement`); the human readable
  line with parentheses is drawn by the app's renderer only (printers cannot print it).
- Code: `js/components/barcode/code128.js` already supports FNC1 at the start and mid-symbol; no AI table in the repo (`gs1.js` to be created);
  TPCL `XB N` reads as `unknown` today; ZPL keeps `e` / `m` in `native` without applying them. Touch list: S2 gs1.js, code128.js, render.js,
  validate.js, constants.js; S3 the three `js/components/barcode/{tpcl,tspl,zpl}.js` and `js/languages/tpcl.js`; S4 LABELS and the select fields.
- The AI table (fixed lengths, mod-10 AIs 00, 01, 02, 410-415) must be checked against the GS1 General Specifications before coding: it is
  not in the repo.

## Verified AI table (research 2026-10-13, source: https://ref.gs1.org/ai/GS1_Application_Identifiers.jsonld)
N = digits, X = GS1 character set 82. "FNC1" = a separator must follow when more data comes after the AI.
- Fixed, numeric, no FNC1: 00 (N18, mod 10), 01 (N14, mod 10), 02 (N14, mod 10), 11 / 13 / 15 / 17 (N6 YYMMDD), 20 (N2), 410-415 (N13, mod 10).
- Variable, FNC1 when not last: 10 (X..20), 21 (X..20), 30 (N..8), 37 (N..8), 240 (X..30), 241 (X..30), 400 (X..30).
- Mod 10 (GS1): weights 3,1,3,1... from the rightmost payload digit; check = (10 - sum mod 10) mod 10. Example SSCC payload `00042273000000113`
  gives check 1 (`000422730000001131`, vendor example); GTIN-14 `1234567890123` gives 1 (`12345678901231`, our own example).
- Character set 82 = `! " % & ' ( ) * + , - . /`, digits, `: ; < = > ?`, `A-Z`, `_`, `a-z` (no space, `# $ @ [ \ ] ^` backtick `{ | } ~`).
- Dates: month 01-12, day 00-31 (no day-versus-month check).
- GS1-128: FNC1 right after the start character; no more than 48 data characters (UNVERIFIED whether AIs count: assume they do, FNC1
  separators included, start / leading FNC1 / check / stop excluded).
- UNVERIFIED (the General Specifications PDF was not reachable): the exact mod-10 text, the day-00 meaning, parentheses in the human readable
  line (usual rule: shown, never encoded). Re-check against the PDF when available; the diagnostics for these are warnings, not errors.

## S4 notes (2026-10-13)
- Select: `TYPE_CODES['gs1-128']` in the three barcode slices (TPCL `9`, TSPL `128M`, ZPL `BC`) makes **Tipo de código** offer GS1-128 (`LABELS` already had it). The type of a gs1-128 item is the same command as Code 128, so the symbology field reads the item to tell them apart.
- Content: the panel shows `item.data` (the parenthesized notation) with `PB.gs1.NOTATION_HINT` as the field note; the edit writes the Code 128 form (`toCode128Data`: TPCL `>8`, TSPL `EAN128` / `128M` + `!102` chosen again with the type, ZPL `>8` and `>0` for a real `>`). A notation that does not encode (`toCode128Data` null) is refused: text unchanged. Cases that would be read back differently are refused too (TPCL a literal `>8`, TSPL `!nnn` in a 128M value).
- Type switch: Code 128 <-> GS1-128 rewrites only the data (to GS1-128 the data must be an element string in the notation; back keeps the notation as text, so the round trip restores the original text). Any other change from or to GS1-128 is refused (the FNC1 data would be lost). TPCL does it in `js/languages/tpcl.js` `updateItem` (same `XB` command), TSPL and ZPL in the slice `reemit`.
- Diagnostics: no new code, the S2 `validate` (`gs1.parse`) shows them after the edit (unknown AI, length, characters, mod 10 with the expected digit, month / day, 48 characters). Writers: `PB.gs1.unwritableMessage` replaces "sin equivalente en X" for a gs1-128 item that cannot be encoded.
- Known gap (closed in S5): a refused edit (structural error) leaves the text unchanged and the field goes back to the previous value, with no message about the rejected input.
- Changed expectations: `tests/barcode-selector.test.js`, `tests/ean-languages.test.js`, `tests/linear-languages.test.js` and `tests/zpl-barcodes.test.js` (the select lists GS1-128 last; an EAN128 element string is a gs1-128 item), `tests/gs1-languages.test.js` (new warning wording).
- README: section *GS1-128 barcodes* (notation, logistic subset only, what the app adds, diagnostics, switching, conversion, not verified). It says the mod 10 digit is validated, not added (S1 had assumed the app would write it; S5 corrected the S1 findings).
- Not checked in a browser (no browser here): the panel behavior is covered through `describeItem` / `updateItem`.
